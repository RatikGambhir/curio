# Spaces API plan

Status: proposal. This is the first, standalone Spaces slice for `curio-service`. It adds a user-owned `spaces` table and create, list, and delete endpoints. Space updates and assigning documents, tasks, calendar events, or chats to a Space are separate follow-up work. The [Tasks API plan](tasks-api-plan.md) depends on this table.

## Contract and scope

A Space belongs to exactly one user. Its `id` is globally unique; its name is unique within that user's Spaces, ignoring case. Two users may use the same name. A user may own resources without any Space. A Space ID never replaces a user ID as the authorization boundary.

The current bearer middleware treats the bearer token as a development user ID. These routes use `CurrentUser.id` as the owner. Creating a Space requires an existing `users` row for the foreign key; listing with an unprovisioned bearer returns an empty page and deleting with one returns `404`. This is owner scoping under the current development auth model, not production authentication. No request body or query parameter can choose `ownerId` or `userId`.

This slice does **not** add `space_id` to existing resource tables, move resources, add a Space update route, or change existing calendar/document/chat endpoints. Once resources reference Spaces, deleting a Space must leave those resources owned by the user and standalone. A membership migration must update the delete use case and tests before it ships; the current direct delete statement is valid only while no resources reference Spaces.

## PostgreSQL schema

Add one append-only SQLx migration under `curio-service/migrations/postgres/`. Keep the `spaces` table generic: no task-specific columns or polymorphic resource rows.

```sql
CREATE TABLE spaces (
    id text PRIMARY KEY,
    owner_id text NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    name text NOT NULL,
    description text,
    created_at timestamptz(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at timestamptz(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    CONSTRAINT spaces_owner_id_key UNIQUE (owner_id, id),
    CONSTRAINT spaces_name_check
        CHECK (name <> '' AND name = btrim(name) AND char_length(name) <= 120),
    CONSTRAINT spaces_description_check
        CHECK (description IS NULL OR char_length(description) <= 2000)
);

CREATE UNIQUE INDEX spaces_owner_name_ci_idx
    ON spaces (owner_id, lower(name));

CREATE INDEX spaces_owner_created_idx
    ON spaces (owner_id, created_at DESC, id DESC);
```

`id` is generated by the service as a UUID string, following the existing public-ID convention. The owner FK matches the current `users.id text` key. The composite unique key allows later child tables to enforce `(owner_id, space_id) -> spaces(owner_id, id)` so a resource cannot attach to another user's Space. The case-insensitive index is scoped by owner; confirm its behavior under the database collation used in CI/deployment. No `space_id` member FK is part of this migration.

The service trims names and descriptions before insert, rejects control characters, enforces the length limits above, and maps a duplicate owner/name index violation to `409`. Make the create DTO reject unknown fields. Use bound SQL parameters and `INSERT ... RETURNING`; do not derive IDs or owner from client input. `created_at` and `updated_at` are UTC millisecond timestamps. Since updates are deferred, they initially match at creation; the future update API will advance `updated_at`.

## HTTP API

All routes are under `/v1/spaces`, protected in `app/bootstrap.rs` by the existing bearer middleware. JSON field names are camelCase. A Space record is `{id,name,description,createdAt,updatedAt}`; `description` may be null. Responses never expose other users' records.

| Method/path | Request | Success | Failure |
| --- | --- | --- | --- |
| `POST /v1/spaces` | `{ "name": "Research", "description": "Optional text" }`; only `name` is required | `201` with the committed Space record | `400` malformed JSON/unknown fields; `401` absent bearer; `409` duplicate name for this user; `422` invalid fields or missing user profile |
| `GET /v1/spaces` | `limit` 1–100 (default 50), optional opaque `cursor` | `200 { "spaces": [...], "nextCursor": null|string }` | `400` invalid query/cursor; `401` absent bearer |
| `DELETE /v1/spaces/{id}` | No body | `204` with no body | `401` absent bearer; `404` missing or foreign Space |

List order is `(created_at DESC, id DESC)` with keyset pagination. The cursor carries those two values and is rejected if malformed; every page query still includes `WHERE owner_id = <current user>`. A cursor does not grant access. The list returns an empty array and null cursor for a user with no Spaces. The delete statement is owner-scoped (`DELETE ... WHERE id = $1 AND owner_id = $2 RETURNING id`), so foreign and missing IDs have the same `404` behavior. Repeating a successful delete returns `404`.

Use a bounded JSON body limit for `POST`. The handler maps feature errors to sanitized `{ "error": "..." }` bodies where a body is returned; the existing bearer middleware's empty `401` remains as-is. Do not describe this as a service-wide error envelope.

## Implementation steps

1. Add the migration, then update `curio-service/ops/postgres/verify.sql` and both expected-table lists and the count in `src/bin/curio_db.rs`. PostgreSQL is now the only database; there is no SQLite importer to update.
2. Add `src/domains/spaces/{mod,model,route,handler,service,repository}.rs`. Put validation and the Space record in `model.rs`, use cases in `service.rs`, owner-scoped SQL in `repository.rs`, and HTTP extraction/status mapping in `handler.rs`. Keep `Database` responsible for pool and migration lifecycle only.
3. Register `domains::spaces` in `domains/mod.rs`, construct the service from the shared database in `app/bootstrap.rs`, and merge the Space routes inside `protected(...)`. The small public `app()` helper is not the full production router; use `app_with_database` for full-router tests.
4. When a client needs Spaces, add `web/src/api/spaces.ts` and its wire/transport tests. Keep API paths relative so both browser and Tauri targets use their existing platform adapters. No new UI or platform capability is required by this service-only slice.
5. Update `docs/ARCHITECTURE.md` when the table and routes are implemented, and deployment notes if migration order or operator steps change. Apply the migration with `curio_db migrate` before starting the service version that verifies it; do not run DDL at service startup.

## Verification and acceptance

- Unit tests: trimmed/empty/oversized/control-character names and descriptions, duplicate-name normalization, and cursor validation.
- Full-router tests: bearer requirement, request and response JSON, empty/list pagination, duplicate name, missing profile, delete success, repeat delete, and foreign-owner delete returning the same `404` as a missing ID.
- PostgreSQL tests in a disposable `curio_test_*` schema: constraints and indexes, per-user name uniqueness, two users with the same name, owner-scoped reads/deletes, reconnect durability, and no changes to unrelated rows.
- From `curio-service`, run `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, and `cargo test` with a safe `CURIO_TEST_DATABASE_URL`. Run `curio_db verify` only against an explicitly safe migrated schema. A green test run without the database variable is not a PostgreSQL pass.
- Inspect the final diff, run `git diff --check`, and perform the mandatory architecture-impact check. Keep unrelated worktree changes untouched.

Acceptance: a user can create a uniquely named Space, list only their own Spaces in bounded pages, and delete one of their own Spaces. Another user may create the same name but cannot see or delete that Space. There is no update endpoint in this slice.
